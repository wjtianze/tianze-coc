# 三个模型的架构与训练规划（草案）

> 状态：规划，未实现。按计划在 19 本版本迁移完成后实施（见工作区《版本更新说明》）。
> 前置接口见 [models.md](models.md)。

## 0. 目标与约束

| 模型 | 输入 | 输出 |
| --- | --- | --- |
| 摆阵 | 防守方账号（建筑/陷阱及等级、可选援军）、难度模式 | 若干阵型（坐标 + 防守援军 + 可切换模式） |
| 配兵 | 进攻方账号（单位等级、容量）、难度模式，可选：对手阵型 | 若干套配兵（兵种/法术/攻城/英雄+装备+战宠+模式） |
| 进攻 | 公平视角下的对手阵型、己方配兵、实时战场、难度模式 | 开战前决策（攻城机器、大守护者模式）+ 逐步部署动作 |

**五种难度模式**：普通、传奇杯 3、传奇杯 2、传奇杯 1、电竞。这是游戏规则（战斗属性调整），见第 1 节。

**随机性**：输入完全相同时输出也可以不同。三个模型都输出概率分布、按种子采样，而不是取最大值。

**约束**
- **部落冲突没有高质量回放，训练只能靠自对弈**。正式服阵型和回放也拿不到。
  FirstLight CR 的路线是"25 万局人类回放模仿学习 → PPO"，我们没有第一步，冷启动改用规则脚本 + 课程学习。
- 模拟器是确定性的：同一阵型、同一配兵、同一动作序列，结果完全相同。随机性必须由模型的采样产生。
- 所有输出都必须先过 `account/layout/army.validate`；进攻动作由环境做合法性屏蔽。

## 1. 难度模式（游戏规则，不是模型能力分档）

五种难度是游戏自带的**战斗属性调整**，定义在 `assets/logic/battle_modifiers.csv`（18.647）。
界面用 `TID_MODIFIER_*` 模板按表中数值显示；旧的固定说明文字（`TID_HARD_MODE_MINUS_*_DESC`，
如"传奇杯 1：防御设施 +15%"）已与表不一致，**以表为准**。

| 模式 | 表中名称 | 防御设施伤害 | 防守方英雄 伤害/生命 | 防守方守卫 伤害/生命 | 进攻方英雄 伤害/生命 | 进攻方装备 |
| --- | --- | --- | --- | --- | --- | --- |
| 普通 | （无调整） | — | — | — | — | — |
| 传奇杯 3 | Minus Three | +10% | +10% | +5% | −5% | — |
| 传奇杯 2 | Minus Two | +15% | +15% | +10% | −10% | — |
| 传奇杯 1 | Minus One | +20% | +20% | +20% | −20% | — |
| 电竞 | Hard Mode | +25% | +25% | +20% | −20% | 普通装备 −3 级，史诗装备 −6 级 |

说明：
- 防御设施那一行的 `Spells` 列为 TRUE，推测防御建筑放出的法术类伤害（如法术塔）也一并增加，需真机确认。
- 传奇杯 1/2/3 在排位战中按所在联赛自动生效；友谊战发起时可选择"应用战斗属性调整"。
- 19 本版本的数值可能变化，迁移时重新读表（规则表生成脚本里加入这张表）。

**对三个模型的影响**：难度模式是三个模型的**条件输入**（一个模式嵌入）。
- 进攻模型：同一个阵型，电竞模式下防御更痛、自己的英雄更脆、装备降级，打法要更保守（例如更依赖法术和兵海，英雄更晚进场）。
- 配兵模型：模式改变英雄和装备的价值，例如电竞下英雄被削 20%、装备降级，配兵可能更偏向兵种和法术。
- 摆阵模型：防守方在高难度下防御伤害和英雄增强，阵型可以更多围绕英雄和高伤害防御来设计。
- 训练时每局随机抽一种模式，按模式分别统计成绩；联赛和 Elo 也按模式分开计算。

**模拟器支持（已完成，真机验证）**：EnemyHomeData 负载的最后 4 字节是本局属性调整的 GlobalID
（0 = 普通，92000000 电竞，92000001 传奇杯 1，92000002 传奇杯 2，92000003 传奇杯 3）。
`tianze_coc/battle_modifier.py` 读写该字段，`selfplay.Match(mode=...)` 指定模式；各模式增益已写入 `progression.json` 的 `battle_modifiers`。
`tools/modifier_check.py` 实测进攻方野蛮人之王生命上限：传奇杯 3 = 0.950 倍、传奇杯 2 = 0.900、传奇杯 1 = 0.800，与表一致；
电竞 = 0.756（−20% 之外装备还降级，装备的生命加成也减少）。防守方英雄和防御设施的增益尚未单独实测。

## 1b. 随机性

同样输入、同样模式下，输出也要能不同：
- 三个模型都输出概率分布，按种子采样（温度 / top-p 可调）；
- 训练时加熵奖励，联赛中保留多样的对手池，防止策略收敛成单一套路；
- 摆阵和配兵先采样 N 个候选，用评估器打分，在"接近最优"的候选里随机挑一个，保证随机的同时不明显变差。

## 2. 进攻模型（最先做，另外两个模型的训练都依赖它）

### 2.1 观测编码
- **实体序列**：每个建筑/单位一个 token = 类型嵌入（GlobalID）+ 等级 + 坐标 + 血量比例 + 阵营 + 状态。
  用 Transformer 编码（实体数可变，最多约 500）。
- **空间图**：50×50 网格（`layout.encode_grid` 的进攻方视角版本 + 实时血量/单位密度通道），用小型 CNN 编码。
- **全局向量**：时间、星数、摧毁率、大本营是否被摧毁、剩余兵力/法术/攻城机器/援军、已用英雄技能、难度模式嵌入。
- **记忆**：LSTM（FirstLight CR 用循环网络；OpenAI Five 同样用 LSTM）。
- 公平视角：陷阱和未现身的特斯拉不进入观测（环境已实现）。

### 2.2 动作（分层自回归 + 合法性屏蔽）
1. 动作类型：等待 k 子帧 / 部署兵种 / 法术 / 英雄 / 援军 / 攻城机器 / 技能 / 回溯重部署。
2. 选单位：只能选还有剩余的（屏蔽）。
3. 选位置：50×50 热力图（GridNet 式空间动作），屏蔽不可部署格子；法术可放在地图内任意格。
4. 数量：一次部署 1/2/4/全部 中的一档（减少决策步数）。

另有一个**开战前头**：根据对手阵型选攻城机器、大守护者模式（对应 `env.prepare`）。

参考：Gym-μRTS / MicroRTS 的无效动作屏蔽与 GridNet 空间动作；AlphaStar 的自回归动作头与指针网络。

### 2.3 训练
1. **规则基线**（无需 GPU）：常见打法脚本，例如单边铺兵开口、英雄跟进、法术打防空，
   作为早期对手、示范数据来源和评估基线。
2. **冷启动（可选）**：用规则脚本自己打出的对局做少量行为克隆，只为解决"会开局、会下兵"，之后完全交给 PPO。
   也可以跳过这步，直接用课程学习：先打低本、弱阵型、短时限，再逐步加难。FirstLight CR 早期也卡在"学会开始一局战斗"。
3. **PPO**：
   - 奖励 = 终局星数（3 星权重最高）+ 摧毁率；过程奖励只用摧毁率增量；对一直不下兵、战斗结束时兵还没下完的情况给轻罚。
   - **对手（阵型）分布**：随机合法阵型（`random_layout`）、规则阵型、历史摆阵模型的阵型，按比例混合。
   - 大本营等级、配兵也随机抽，覆盖 9～19 本。
4. 实现参考：CleanRL（PPO 单文件实现，适合起步）、Sample Factory（异步高吞吐，适合多模拟器实例）。

### 2.4 评估（吸取 FirstLight CR 的教训）
- 固定一套"基准阵型集"（各本、各风格），报告平均星数、3 星率、摧毁率。
- 每个候选模型都要**看回放**：确认不是靠环境漏洞或对手阵型太弱刷分。
  FirstLight CR 曾对着被动的 IL 对手刷出 80% 胜率，其中 296/306 胜是对手几乎没出牌的对局。

## 3. 配兵模型

### 3.1 架构
- **输入**：单位等级表（每个可用单位一个 token：类型 + 等级 + 是否解锁）、容量、难度模式；
  可选：对手阵型摘要（实现"针对阵型配兵"时用）。
- **输出**：自回归生成一个集合。每步选"加一个单位/法术/攻城机器/英雄/装备/战宠/结束"，
  剩余容量和规则（超级兵 ≤ 2 种、装备属于英雄等）实时屏蔽，保证每次采样都合法。
- 同一输入采样多次，得到多套不同配兵（随机性）。

### 3.2 训练
- 本质是**上下文多臂老虎机**：一套配兵的价值 = 进攻模型用它去打一批阵型的平均结果。
- 模拟很贵，所以训练一个**替代评估器**（配兵 + 阵型特征 → 预测星数/摧毁率），用真实模拟结果持续更新。
- 生成器用 REINFORCE/PPO 优化评估器分数，定期抽样做真实模拟校正。
- 难度模式：作为输入，评估时在同一模式下模拟。

## 4. 摆阵模型

### 4.1 架构
两阶段生成（参考 PCGRL：把关卡生成当成强化学习的逐步放置问题）：
1. **建筑放置**：自回归逐件放置。Transformer 编码"已放置的网格 + 待放清单"，
   用指针网络选下一件，用空间热力图选位置；越界和重叠格子屏蔽。
2. **城墙与陷阱**：城墙按"隔间"图生成（先决定围哪些建筑，再生成闭合墙线）；陷阱单独放在空格上。
3. 防守援军、精工防御三选一、改装模式作为额外的离散输出头。

### 4.2 训练（对抗）
- 奖励 = −（进攻方在这个阵型上的期望结果），进攻方 = 进攻模型 + 配兵模型，在同一难度模式下多次采样取平均。
- 这是 **PAIRED / 对抗式环境设计**的形式：摆阵模型就是"设计关卡的对手"。合法性由校验器保证，不会生成不可能的阵型。
- 同样配替代评估器（阵型 → 被打的期望星数），减少模拟次数。

## 5. 三模型联合：联赛自对弈

参考 AlphaStar 联赛和 PSRO：

```
进攻方种群（进攻模型 × 配兵模型）  ⇄  防守方种群（摆阵模型）
   主力：对全部历史防守方训练             主力：对全部历史进攻方训练
   针对者：专打当前主力防守方的弱点        针对者：专防当前主力进攻方的弱点
   历史快照池：防止遗忘、防止循环克制
```

**顺序**
1. 进攻模型 vs 随机/规则阵型，直到能稳定打出 2 星以上。
2. 加入配兵模型（进攻模型冻结或低学习率）。
3. 加入摆阵模型，对冻结的进攻方做对抗训练。
4. 交替更新，每种难度模式各自建立 Elo 天梯。

**随机性的保障**：熵奖励 + 种群多样性（不同快照、不同针对者）+ 推理时采样；
同时用质量门槛，避免为了随机而输出明显很差的方案。

## 6. 工程与算力

- 模拟器吞吐：锁步加速下约 2.6 秒一局。PPO 需要几十到上百个模拟器实例并行
  （FirstLight CR 用 Linux AVD 集群，每个虚拟机里跑多个引擎进程）。我们也需要类似的多实例方案，这是最大的工程量。
- 模型规模：进攻模型约几百万参数，单卡 GPU 足够；瓶颈在模拟器数量，不在 GPU。
- 每次大版本更新（例如 19 本）后：规则表、命令、离线开局都要重新验证；模型需要在新单位上微调。
  词表按 GlobalID 设计，新单位只需新增嵌入。

## 7. 主要风险
- **只能自对弈**：自对弈可能学出"AI 之间有效、对真人不自然"的打法和阵型，
  要靠多样的对手池和看回放来发现。
- **奖励被钻空子**：例如阵型模型利用模拟器漏洞、进攻模型只追求摧毁率。只能靠看回放和基准集发现。
- **联赛不收敛或循环克制**：用历史池和针对者缓解。
- **模拟吞吐不足**：先用替代评估器顶住配兵/摆阵模型的训练，进攻模型优先占用模拟器。

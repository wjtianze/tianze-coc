# 三个模型的架构与训练规划

> 状态：规划，未实现。按计划在 19 本版本迁移完成后实施（见工作区《版本更新说明》）。
> 前置接口见 [models.md](models.md)。

## 0. 目标与前提

| 模型 | 输入 | 输出 |
| --- | --- | --- |
| 摆阵 | 防守方账号（建筑/陷阱及等级）、难度模式 | 阵型（全部坐标）+ 防守部落城堡援军 + 精工防御与改装模式选择 |
| 配兵 | 进攻方账号（单位/装备/战宠等级、容量）、难度模式，可选：对手阵型 | 一套配兵（兵种、法术、攻城机器、英雄 + 装备 + 战宠 + 大守护者模式、援军请求） |
| 进攻 | 难度模式、公平视角的对手阵型、己方配兵、实时战场 | 开战前决策（攻城机器、大守护者模式）+ 逐步部署动作 |

前提：

1. **难度模式是游戏规则，不是模型强弱**：普通、传奇杯 3、传奇杯 2、传奇杯 1、电竞是游戏自带的战斗属性调整，
   会改变防御和英雄的数值。三个模型在任何模式下都要尽量打出最好的结果，模式作为条件输入（第 1 节）。
2. **只能自对弈**：部落冲突没有高质量回放，正式服阵型也拿不到。所有模型从零开始，靠规则脚本冷启动 + 强化学习自对弈。
   FirstLight CR 的路线是"25 万局人类回放模仿学习 → PPO 自对弈"，我们没有第一步。
3. **随机性**：同一账号、同一模式、同一对手，输出也可以不同；三个模型都输出概率分布、按种子采样（第 6 节）。
4. **合法性**：所有输出先过 `account / layout / army.validate`；进攻动作由环境屏蔽非法选项；
   实时控制私服时，一条非法命令会导致整批修改被服务器丢弃，所以校验是硬性要求。
5. **模拟器是确定性的**：同样的阵型、配兵和动作序列，结果完全相同；随机性只来自模型采样。

## 1. 难度模式

### 1.1 规则（18.647，`battle_modifiers.csv`，已在真机验证）

| 模式 | 负载写入值 | 防御设施伤害 | 防守英雄 伤害/生命 | 防守守卫 伤害/生命 | 进攻英雄 伤害/生命 | 进攻方装备 |
| --- | --- | --- | --- | --- | --- | --- |
| 普通 | 0 | — | — | — | — | — |
| 传奇杯 3 | 92000003 | +10% | +10% | +5% | −5% | — |
| 传奇杯 2 | 92000002 | +15% | +15% | +10% | −10% | — |
| 传奇杯 1 | 92000001 | +20% | +20% | +20% | −20% | — |
| 电竞 | 92000000 | +25% | +25% | +20% | −20% | 普通装备 −3 级，史诗装备 −6 级 |

- 实测：进攻方野蛮人之王生命上限在传奇杯 3/2/1 下为普通的 0.950 / 0.900 / 0.800 倍；
  电竞为 0.756 倍（装备降级使装备的生命加成也减少）。防守方英雄与防御设施的增益尚待单独实测。
- 适用场景：排位战按所在传奇杯联赛自动生效；友谊战发起时可选择；常规联机为普通。

### 1.2 模式如何进入模型

不只给一个模式编号，而是给**数值化的模式向量**，让模型理解"这个模式改了什么"，
19 本出新模式或改数值时无需重训编号嵌入：

```
mode_vec = [防御伤害%, 防御生命%, 防守英雄伤害%, 防守英雄生命%, 守卫伤害%, 守卫生命%,
            进攻英雄伤害%, 进攻英雄生命%, 普通装备降级, 史诗装备降级, 是否影响法术类伤害]
         + 模式编号的嵌入（捕捉表外的差异）
```

数值从 `progression.json` 的 `battle_modifiers` 读取。另外，**电竞模式下装备的"有效等级"**
（实际等级 − 降级数，下限 1）直接写进单位 token，模型看到的就是本局真实生效的数值。

### 1.3 模式对三个模型的影响（预期，需要训练结果验证）

- **进攻**：高难度下防御更疼、英雄更脆，英雄进场时机、法术保护和开口方式都会改变。
- **配兵**：英雄被削弱、电竞装备降级，兵种与法术的相对价值上升；装备选择要按降级后的等级重新评估。
- **摆阵**：防守英雄和守卫被加强，阵型可以更多围绕英雄、守卫和高伤害防御来布置；
  排位战的防守阵型面对的是该联赛模式的进攻，应该按该模式优化。

### 1.4 模式与场景

| 场景 | 模式 | 摆阵模型优化目标 |
| --- | --- | --- |
| 排位战（传奇杯 3/2/1） | 自动随联赛 | 该联赛模式下被打的期望星数最低 |
| 友谊战 | 发起方选择 | 发起时选定的模式 |
| 常规联机 | 普通 | 普通模式 |
| 电竞（友谊战选择） | 电竞 | 电竞模式 |

防守部落城堡援军只有排位战和友谊战可以自定义，摆阵模型只在这两种场景输出援军。

## 2. 共用的编码器

三个模型共用同一套输入表示（可以共享预训练权重）：

- **单位/建筑 token**：类型嵌入（GlobalID）+ 等级（装备按本局有效等级）+ 坐标 + 状态（血量比例、阵营、是否已现身）。
- **空间图**：50×50 网格（`layout.encode_grid`，进攻方视角去掉陷阱和未现身的特斯拉），小型卷积网络编码。
- **全局向量**：大本营等级、容量、模式向量（1.2 节）、时间等。
- 实体用 Transformer 编码，最多约 500 个；GlobalID 词表，新单位只需新增嵌入。

## 3. 进攻模型（最先训练，另外两个模型的评估都依赖它）

### 3.1 架构
- 编码：共用编码器 + LSTM 记忆（FirstLight CR、OpenAI Five 都使用循环策略）。
- **开战前头**：看对手阵型（公平视角）与模式，选本局攻城机器（自己的或援军的）和大守护者模式（对应 `env.prepare`）。
- **部署头**（分层自回归，非法选项屏蔽）：
  1. 动作类型：等待 k 子帧 / 兵种 / 法术 / 英雄 / 援军 / 攻城机器 / 技能 / 回溯重部署；
  2. 选单位：只能选还有剩余的；
  3. 选位置：50×50 热力图（GridNet 式空间动作），屏蔽不可部署的格子；
  4. 数量：1 / 2 / 4 / 全部（减少决策步数）。
- 价值头：预测本局星数和摧毁率（以模式向量为条件）。

### 3.2 训练
1. **冷启动**（二选一或组合）：
   - 规则脚本：常见打法（单边铺兵开口、英雄跟进、法术打关键防御），作为早期对手和少量行为克隆的来源；
   - 课程学习：先打低本、弱阵型、普通模式，逐步加难。
2. **PPO 自对弈**：
   - 奖励：终局星数（3 星权重最高）+ 摧毁率；过程奖励只用摧毁率增量；兵没下完就结束时轻罚，防止消极。
   - 每局随机抽**模式**（课程：先普通为主，逐步提高高难度模式比例，最终五种均衡）、大本营等级、配兵和对手阵型；
   - 对手阵型：随机合法阵型、规则阵型、历史摆阵模型的阵型按比例混合。
3. 实现参考：CleanRL（PPO 起步）、Sample Factory（多模拟器实例异步高吞吐）。

### 3.3 评估
- 每种模式一套固定基准阵型（各本、各风格），分别报告平均星数、3 星率、摧毁率。
- 模式之间应符合常识：同一阵型、同一配兵，模式越难成绩越低；不符合时优先怀疑环境或注入。
- 每个候选模型都要看回放。FirstLight CR 曾对着被动对手刷出 80% 胜率，其中 296/306 胜来自对手几乎没出牌的对局。

## 4. 配兵模型

### 4.1 架构
- 输入：共用编码器编码单位等级表（每个单位 token 带"是否解锁、等级、本局有效等级"）、容量、模式向量；
  可选：对手阵型摘要（"针对阵型配兵"时使用）。
- 输出：自回归生成一个集合。每步选"加入一个兵种/法术/攻城机器/英雄/装备/战宠/援军请求/结束"，
  剩余容量和规则（超级兵 ≤ 2 种、装备属于该英雄、战宠不重复、只有大守护者有模式）实时屏蔽，保证每次采样都合法。

### 4.2 训练
- 本质是**上下文多臂老虎机**：配兵的价值 = 进攻模型在同一模式下用它打一批阵型的平均结果。
- 模拟很贵：训练一个**替代评估器**（配兵 + 阵型 + 模式 → 预测星数/摧毁率），用真实模拟结果持续更新；
  生成器用 REINFORCE/PPO 优化评估器分数，定期抽样做真实模拟校正。
- 对手阵型来自摆阵模型（同一模式）和随机阵型的混合。

## 5. 摆阵模型

### 5.1 架构
两阶段生成（参考 PCGRL：把关卡生成当成逐步放置的强化学习问题）：
1. **建筑放置**：自回归逐件放置。Transformer 编码"已放置的网格 + 待放清单 + 模式向量"，
   指针网络选下一件，空间热力图选位置；越界和重叠格子屏蔽。
2. **城墙与陷阱**：城墙按"隔间"生成（先决定围哪些建筑，再生成闭合墙线）；陷阱单独放在空格上。
3. 离散输出头：防守援军（仅排位战/友谊战场景）、精工防御三选一、改装模式。

### 5.2 训练（对抗）
- 奖励 = −（同一模式下进攻方在这个阵型上的期望结果），进攻方 = 进攻模型 + 配兵模型，多次采样取平均。
- 这是 **PAIRED / 对抗式环境设计**的形式：摆阵模型就是设计关卡的对手；合法性由校验器保证。
- 同样配替代评估器（阵型 + 模式 → 被打的期望星数），减少模拟次数。

## 6. 随机性

- 三个模型都输出概率分布，按种子采样；温度、top-p 可在推理时调节。
- 训练时加熵奖励，联赛中保留多样的对手池，防止收敛成单一套路。
- **质量门槛**：摆阵和配兵先采样 N 个候选，用替代评估器打分，只在"接近最优"的候选里随机挑一个，
  保证随机的同时不明显变差。进攻在价值接近的动作之间按概率采样。
- 同一输入的多样性单独评估：多次采样的结果之间的差异（阵型编辑距离、配兵差异、部署路线差异）要高于阈值。

## 7. 三模型联合：联赛自对弈

参考 AlphaStar 联赛和 PSRO：

```
进攻方种群（进攻模型 × 配兵模型）  ⇄  防守方种群（摆阵模型）
   主力：对全部历史防守方训练             主力：对全部历史进攻方训练
   针对者：专打当前主力防守方的弱点        针对者：专防当前主力进攻方的弱点
   历史快照池：防止遗忘、防止循环克制
```

- 所有模型都是**模式条件**的单一网络，不为每个模式单独训练一套；每局随机抽模式。
- Elo 和成绩**按模式分别统计**，用来发现某个模式下的退化。

训练顺序：
1. 进攻模型 vs 随机/规则阵型，普通模式为主，直到能稳定 2 星以上；再把五种模式逐步加入。
2. 加入配兵模型（进攻模型冻结或低学习率）。
3. 加入摆阵模型，对冻结的进攻方做对抗训练。
4. 三者交替更新，形成联赛。

## 8. 工程与算力

- 每局对局由 `selfplay.Match(defender, attacker, army, layout, mode)` 组装，离线开局；锁步加速约 2.6 秒一局。
- 瓶颈是模拟器数量而不是 GPU：PPO 需要几十到上百个实例并行。FirstLight CR 用 Linux 虚拟机集群、每台多个引擎进程，
  我们也需要类似的多实例方案，这是最大的工程量。
- 模型规模：进攻模型约几百万参数，单卡 GPU 足够。
- 版本更新（例如 19 本）后：规则表、属性调整表、命令格式、离线开局都要重新验证；新单位只需新增嵌入，模式向量自动从新表读取。

## 9. 主要风险

- **只能自对弈**：可能学出"AI 之间有效、对真人不自然"的打法和阵型。靠多样的对手池、基准集和看回放发现；
  以后可以在私服和真人打友谊战（实时模式）检验。
- **奖励被钻空子**：例如摆阵模型利用模拟器漏洞、进攻模型只追求摧毁率。
- **模式间失衡**：共享网络可能偏向样本多的模式；按模式统计成绩，必要时调整抽样比例。
- **联赛不收敛或循环克制**：用历史池和针对者缓解。
- **模拟吞吐不足**：配兵、摆阵模型先靠替代评估器，进攻模型优先占用模拟器。
